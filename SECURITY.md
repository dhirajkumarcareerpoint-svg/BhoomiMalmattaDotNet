# SECURITY

* **Authentication:** ASP.NET Forms Authentication (encrypted ticket, HttpOnly, SameSite=Lax, Secure in release, 20-minute sliding timeout, new session id on sign-in, logout clears cookies). Passwords: existing **bcrypt** hashes verified with BCrypt.Net; plaintext is never stored or logged. No default or hard-coded credentials. Login throttling and rate limiting on public endpoints.
* **Authorization:** role and zone come only from the server-side ticket, never from the browser. Enforced in page base classes and API `[Authorize(Roles=...)]`, and again inside the workflow service (a JE cannot do OS work; OS cannot give final approval; levels cannot be skipped; finalized applications are immutable except an explicit Admin/AC reopen).
* **Concurrency:** optimistic concurrency on the existing `RowVersion`; stale-stage and duplicate submissions are rejected.
* **CSRF/XSS:** ViewStateUserKey per session; API state-changing calls require a custom header; output encoding; CSP and security headers in `Web.config`.
* **Files:** extension allow-list (pdf/jpg/png), MIME + magic-number validation, 5 MB limit, generated storage names, sanitized display names, path-traversal rejection, relative paths only in the database, storage outside the web root, officer-only access to identity/address documents.
* **Citizen access:** applicants track by application number only. Numbers are sequential and guessable (accepted for the current workflow); the page and status API allow 30 lookups per IP per 10 minutes, return the same generic failure, and delay not-found responses. Successful lookup issues a short-lived ticket bound to one application. Applicant views mask mobile/email and omit identity/PAN, officer identity, internal remarks, hashes, IPs, correlation ids and physical paths. Reconsider adding a second factor before production exposure. The existing ApplicantAccessTokenHash remains populated but is no longer requested for lookup.
* **Database:** startup guard requires database `SMC_BhoomiMalmatta`; no initializer, migration, or DDL anywhere in the code; SQL is parameterized (EF / parameters). A least-privilege SQL login is recommended.
* **Logging:** correlation id per request; no passwords, tokens or personal data in logs; connection strings are redacted.
* **Known limitations:** `IdentityNumber` and `PanNumber` columns are `nvarchar(max)` in the existing database and are stored as the application receives them - application-level encryption is recommended as a future change. QuestPDF Community licence eligibility must be confirmed by the Corporation. ACL gateway parameters are unverified.
